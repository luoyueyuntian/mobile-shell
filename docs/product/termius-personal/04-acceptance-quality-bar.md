# Acceptance And Quality Bar

## 目标

这一份文档定义“什么时候算做完”，避免后续 AI 只完成表面 UI 或只把代码编进去，却没有真正满足产品行为。

## 首发版本验收门槛

首发版本必须同时满足下面四类门槛。

### 1. 产品范围门槛

必须覆盖以下 `P0` 能力：

- Host 管理
- 分组、标签、搜索
- SSH 终端
- SFTP 基本文件工作流
- 身份、密钥、密码与证书管理
- Known Hosts 信任流程
- 端口转发
- 命令片段
- 本地工作区和基础日志/历史

如果缺失其中任意一项，则不能宣称“个人版基础工作台已可发布”。

### 2. 质量门槛

- 新增或修改的行为必须有 XCTest 覆盖
- 关键路径失败必须向用户显示错误，而不是静默失败
- 删除、覆盖、断开等 destructive actions 必须有明确确认或可恢复路径
- 应用重启后，主机、规则、片段、工作区等本地数据必须可恢复
- 已保存凭证不能因普通数据持久化失败而丢失

### 3. 架构门槛

- 不把新功能继续堆进 `ShellRootView.swift` 大块 UI
- 不把新的跨领域逻辑继续堆进 `Models.swift`
- 任何 SSH、SFTP、端口转发的外部库细节都不能直接从 view 层触达
- 持久化逻辑与 UI 决策必须分层

### 4. 交互门槛

- 用户能在少量操作内从主机列表到达目标动作
- 常见任务流必须连续，例如打开终端、进 SFTP、执行片段、启停转发
- 空状态、加载状态、错误状态必须可理解

## 单功能切片完成定义

后续每个功能切片都必须满足下面的完成定义：

1. 需求边界明确
2. 代码落在正确模块，而不是继续堆热点文件
3. 行为测试新增或更新
4. 目标测试通过
5. 相关文档已同步
6. 未引入本项目明确排除的团队或企业概念

## 手工验收场景

以下场景是首发版本至少要能顺畅完成的人工检查项。

### 场景 1：首次添加主机并连接

- 创建 Host
- 保存密码或 identity
- 打开 SSH 终端
- 遇到未知主机时完成信任流程
- 成功进入可交互 shell

### 场景 2：用标签和搜索找到主机

- 创建多台主机和多组标签
- 用标签筛选
- 用搜索定位某台机器
- 直接进入终端或 SFTP

### 场景 3：在 SFTP 中完成基本文件任务

- 进入某个目录
- 上传文件
- 下载文件
- 重命名文件
- 删除文件或目录

### 场景 4：启用端口转发

- 创建本地转发规则
- 启动规则
- 看到运行中状态
- 停止规则
- 失败时能读懂错误

### 场景 5：执行命令片段

- 创建片段
- 在当前终端会话里发送片段
- 输出进入终端或日志上下文

### 场景 6：工作区上下文恢复

- 创建至少一个工作区
- 把会话归入工作区
- 切换工作区
- 重启应用
- 工作区元数据仍存在，主要上下文没有消失

## 非功能要求

### 数据可靠性

- 本地数据结构演进必须保持向后兼容
- 缺失字段必须有安全默认值
- 单条坏数据不应毁掉整个仓库读取

### 安全性

- 密码、私钥、证书不能明文混入普通 JSON
- Known Hosts 流程不能绕过用户确认
- 删除敏感数据时要同步处理关联记录

### 可维护性

- 新文件优先放到目标 feature / service / persistence 目录
- 测试按功能域组织，不继续把所有行为塞进一个大测试文件

## 不允许被当作“已完成”的情况

下面这些情况都不能算完成：

- 只有界面，没有真实状态流和持久化
- 只有 happy path，没有错误处理
- 只有本地假数据，没有接入真实 service seam
- 测试只覆盖内部实现细节，不覆盖用户行为
- 引入了团队概念但没有产品要求

## 验收报告最低要求

每次完成一个功能切片后，汇报至少要包含：

- 这次覆盖了哪些需求项
- 改动落在哪些模块
- 跑了哪些测试
- 有哪些已知未完成项
- 是否引入了新的后续切片
