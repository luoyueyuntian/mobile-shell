# AI Execution Contract

## 目的

这份文档直接约束后续 AI 的工作方式，避免它做出“看起来合理、实际偏题”的实现。

## 开工前必须先读

后续 AI 在动手前，默认按下面顺序读取上下文：

1. `AGENTS.md`
2. `docs/project-constraints.md`
3. `docs/product/termius-personal/README.md`
4. 当前目录下其余文档
5. 与当前切片直接相关的 `docs/superpowers/specs/` 或 `plans/`

## 绝对边界

AI 不得主动做以下事情，除非用户明确要求改变产品方向：

- 引入团队、成员、组织、权限角色
- 引入团队共享 Vault
- 引入多人协作终端、实时共享或 multiplayer
- 引入后台管理台、集中计费、企业合规模块
- 为未来团队版预先设计复杂权限系统
- 为未来云平台预先引入当前用不到的后端框架
- 在当前阶段主动规划或实现个人云同步

## 默认实现假设

如果用户没有额外说明，AI 应默认：

- 平台只考虑 `iOS / iPadOS`
- 用户只有一个人
- 数据以本地持久化为主
- 凭证通过 Keychain 或凭证层管理
- 功能按最小可发布切片交付
- 每次优先做一个垂直能力，而不是横向铺很多半成品

## 功能拆分规则

如果一个任务同时涉及以下任意两项，AI 必须先拆 spec 或 plan，再决定是否实现：

- 新 UI 流程
- 新持久化结构
- 新 service 边界
- 新外部依赖
- 多个 feature 间的共享状态编排

## 优先级判断规则

当需求不明确时，按以下顺序判断优先级：

1. 是否直接提升个人用户日常远程操作效率
2. 是否减少重复输入、重复配置或上下文丢失
3. 是否增强本地可靠性与恢复能力
4. 是否只是“Termius 有，所以也想做”

如果只有第 4 条成立，则默认不优先。

## 架构行为规则

### 必须做

- 新增功能优先落在 `Features/`、`Shared/`、`Services/`、`Persistence/`
- 复用既有领域类型，例如 `ShellHost`、`TerminalWorkspace`、`ShellSnippet`
- 用协议边界包住外部 SSH / SFTP / forwarding 实现
- 用行为测试覆盖新增能力

### 不得做

- 把新屏幕继续大块塞进 `ShellRootView.swift`
- 把无关 store 逻辑继续堆进 `Models.swift`
- 让 view 直接操纵 `Citadel`、`NIO` 或 `Security`
- 把敏感数据直接存到普通 JSON

## 交付策略

AI 应优先输出“可验证的单切片完成”，而不是“宏大但未闭环的半架构”。

推荐交付单位：

- 一个可独立验收的用户行为
- 一个明确的 feature slice
- 一次能跑测试、能说明完成标准的变更

不推荐的交付单位：

- 大规模预重构
- 多个系统同时半完成
- 为未来功能铺设大量当前不用的抽象

## 避免无效工作的检查表

动手前先问自己：

1. 这个需求属于个人版还是团队版？
2. 这是首发必需，还是后续增强？
3. 现有模型里是否已经有接近的类型或概念？
4. 这次改动会不会继续恶化热点文件？
5. 是否真的需要新依赖、新后端、新账号体系？

如果第 1、2、5 任何一项回答不清楚，先缩小范围。

## 需要暂停并重新确认的情况

出现下面情况时，AI 应先停下并给出拆分建议，而不是硬做：

- 用户请求模糊地包含了同步、协作、共享
- 任务开始涉及后台服务、账号系统或冲突解决
- 一个改动需要同时重做 terminal、SFTP、persistence 三层以上
- 功能目标已经超出“个人 SSH 工作台”

## 文档同步规则

实现过程中如果改变了产品边界、需求优先级或架构约束，AI 必须同步更新本目录对应文档，而不是把真正的规则藏进代码里。

## Definition Of Done

AI 只有在以下条件全部满足时，才能宣称一个切片完成：

- 满足明确需求项
- 测试已跑并有结果
- 文档已同步
- 没有越过个人版边界
- 没有把问题转移成新的结构性债务
